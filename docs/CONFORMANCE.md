# XSD 1.0 数据类型一致性说明

这份文档回答三个问题：验证器的**一致性终点**是什么、**词法如何映射到值空间**、
以及各个 facet 在哪个空间上判定。

写它的直接原因是初审意见指出的两处语义问题：`pattern` 用了子串搜索、
`float`/`double` 的枚举按未舍入的十进制比较。两处都已修正，下面写明依据。

---

## 1. 一致性终点

XSD 1.0 Part 2 的验证规则在 §4.1.4（Simple Type Definition Validation Rules）：
给定一个简单类型 T 和一个字符串 S，

1. S 必须匹配 T 的词法空间中的一个字面量（§4.1.4 规则 1，含 whiteSpace 处理）；
2. 该字面量映射到的值必须落在 T 的值空间内，且满足每个 facet（§4.1.4 规则 2）。

本项目的输出就是这两步的结论：

| 输出 | 含义 |
| --- | --- |
| `Ok(value)` | S 是 T 的合法字面量，`value` 是它映射到的值空间元素 |
| `Err(Lexical(..))` | 第 1 步失败：不是词法空间的成员 |
| `Err(Facet(..))` | 第 2 步失败：值合法但不满足某个 facet |

**不做 PSVI。** XSD 允许验证器额外产出类型注解、默认值等后模式验证信息，本项目不产出。
W3C 测试套件本身也不检查 PSVI，所以这不影响一致性结论，但使用者需要知道边界在哪。

**不做内容模型。** 元素能否出现、顺序是否正确属于 Part 1，不在 Part 2 的范围内。

---

## 2. 词法到值空间的映射

映射分三步，顺序不能换：

```
输入 S
  │
  ├─ 1. whiteSpace 规范化（按类型的固定规则：preserve / replace / collapse）
  │
  ├─ 2. 词法空间判定：规范化后的串是否是该类型的合法字面量
  │
  └─ 3. 值映射：按类型规则产生值空间元素（可能发生舍入、规范化、解析）
```

第 3 步是分歧最容易出现的地方，逐类型说明。

### 2.1 `decimal`：精确十进制，不舍入

`xs:decimal` 的值空间是**任意精度的十进制数**，没有指数、没有位数上限。

- `1.230` 与 `1.23` 是同一个值，前者的尾随零属于词法，不属于值；
- `1.0000000000000000000001` 不能塌成 1；
- 比较时对齐小数点逐位比，不经过二进制浮点。

实现上 `Decimal` 保存符号、整数部分、小数部分的字符串，比较与相等都在这个表示上做。

### 2.2 `float` / `double`：IEEE 754，必须舍入

这是初审意见指出的第二处问题，也是本次修改的核心。

`xs:float` 的值空间是 **IEEE 754 binary32**，`xs:double` 是 **binary64**。
一个十进制字面量映射到值空间时，必须落到**最近的**那个可表示值上。

后果是：**不同的字面量可以是同一个值。**

```
0.1
0.10
1E-1
0.1000000000000000055511151231257827
```

这四个都映射到同一个 binary64。所以：

- 若 `enumeration` 写的是 `0.1`，那么实例 `0.1000000000000000055511151231257827`
  必须判定为**合法**；
- 若按写下来的数字串比较，会错误地拒绝它。

`xs:float` 还要多一步：字面量先舍入到 binary32，再作为值参与比较。
`0.1` 作为 float 的值是 `0.100000001490116119384765625`（binary32 精确值），
与它作为 double 的值不同。`enumeration` 与 `minInclusive` 这类 facet 必须看到
**该类型自己的**那个值。

实现：`FloatValue::Finite(Double)`，`double` 直接存 binary64；`float` 解析后经
binary32 舍入再宽化成 binary64。十进制到 binary64 的转换保留 17 位有效数字并对
第 18 位做进位，超出则表示范围时饱和为 `INF` 或 `0`。

> 早期版本把有限值存成 `Decimal`，理由是"避免 0.1 变成 0.1000… 后 enum 失败"。
> 这是把因果弄反了：`enumeration` 应该在**值空间**比较，而值空间里的 0.1 本来就是
> 那个二进制近似值。已改为存机器浮点，并补了针对性测试。

**NaN 是特殊情形。** 它与任何值都不构成有序关系，**包括它自己**。因此：

- 四个边界 facet（`minInclusive`、`maxInclusive`、`minExclusive`、`maxExclusive`）
  对 `NaN` **一律不成立**；
- `enumeration value="NaN"` 永远不会匹配任何实例，连 `NaN` 本身也不匹配。

实现上不能在比较里给 `NaN` 编一个"最大"的序号——那样单侧边界会放行它。

### 2.3 时间类型：字段，不是时间点

`dateTime`、`date`、`time`、`gYear` 等类型的值是**日历字段的组合**，不是一个绝对时刻。

- `2026-02-30` 词法上像一个日期，但 2 月没有 30 日，**值不存在**，判定为非法；
- `24:00:00` 是小时 24 的唯一合法形式，等价于次日 `00:00:00`；
- 时区可选。带时区与不带时区的值**不相等**，也不能直接比大小（XSD 对此有明确说明）。

### 2.4 `QName`：三元组

`QName` 的值是 `(命名空间名, 本地名, 前缀)`。前缀不参与身份判定：
不同前缀绑到同一 URI 就是同一个值。

`length` 系列 facet 在 `QName` 上是 **deprecated**（XSD 1.0 §3.2.18 与 XSD 1.1
都这么说），而且两版都没有定义 QName 的"长度"是什么。本项目跳过这三个 facet。

## 3. facet 在哪个空间上判定

| facet | 作用对象 | 说明 |
| --- | --- | --- |
| `pattern` | **规范化后的词法形式** | 全串锚定，见 3.1 |
| `enumeration` | **值空间** | 按值的相等性比较，见 3.2 |
| `length` / `minLength` / `maxLength` | 字符串按**码点**数，列表按**项**数 | |
| `maxInclusive` 等四个边界 | **值空间**的有序比较 | decimal 按十进制比，float/double 按 IEEE 比 |
| `totalDigits` / `fractionDigits` | 值的十进制表示 | 只对 decimal 及其派生有效 |
| `whiteSpace` | 词法形式 | 由类型固定，不可自由指定 |

### 3.1 `pattern` 是锚定的

XSD 1.0 Part 2 §F 明确：

> Unlike some popular regular expression languages (including those defined by
> Perl and standard Unix utilities), the regular expression language defined
> here **implicitly anchors all regular expressions at the head and tail**

也就是说 `[A-Z]+` 必须匹配**整个**词法形式，`A1` 不合法。
要表达"包含"必须显式写 `.*[A-Z]+.*`。

> 早期版本用了子串搜索，`A1` 会被 `[A-Z]+` 接受。这是错的，已改为全串匹配，
> 并补了 `A1` / `1A` / `A1B2` 三个应当拒绝的用例。

顺带说明为什么 974 个 W3C 用例当时没抓出来：套件里的 pattern 用例大多写成
能覆盖整个词法的形式，两种语义在那些输入上恰好给出同样的结论。这也说明
"套件通过"不等于"语义正确"，边界用例必须自己补。

### 3.2 `enumeration` 按值空间比较

`enumeration` 的成员值在解析时同样要经过词法到值空间的映射，比较发生在值上。

- `decimal`：`1.0` 与 `1.00` 相等；
- `float`/`double`：按 IEEE 值比较，见 2.2；
- `QName`：按三元组比较；
- `hexBinary`/`base64Binary`：按**字节**比较，`0F` 与 `0f` 相等；
- 列表：各项分别映射后逐项比较。

### 3.3 `union` 的 whiteSpace 固定为 collapse

联合类型的空白规则由**类型本身**决定，固定为 collapse，与成员各自的规定无关。
所以 `"  abc  "` 交给一个 `xs:string` 成员时，成员看到的是 `abc`。
不折叠会让 `xs:string` 成员拿到带空白的原串，值也就跟着错了。

## 4. 与测试套件的对照

W3C XML Schema Test Suite（NIST datatypes 贡献）中取 510 个
（variety × type × facet）组合，每个组合一个 valid 加一个 invalid 实例，
共 **974 个用例**，全部一致；974 段真实 schema 全部能解析，0 个解析失败。

外加 **63 个单元测试**，专门覆盖上面这些容易搞反的地方：锚定、舍入、码点计数、
日历合法性、NaN 与 `-0`。

两者互补：套件证明"和官方预期一致"，单元测试证明"我们知道自己为什么一致"。

## 5. 已知偏差

- **Unicode 类别**：`\p{L}`、`\d` 按主要区间判断，未加载完整 UCD 表。
- **年份上限 9999**：更大的年份词法合法，但日历运算按 4 位年份处理。
- **字符类减法**只支持一层。
- **`QName` 的 `length` 系列**：跳过（deprecated 且无定义），见 2.4。
- 不做 XML 1.0 完整 well-formedness 校验。

这些在 README 的「已知限制」与 Issues 里都有对应条目。
